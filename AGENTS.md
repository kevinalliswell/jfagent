Single entry contract for Codex and every AI coding agent on this project.
This UPPERCASE file is the one Codex auto-loads. Read it fully before doing anything.

## 0. Start Here Every Session

1. Run the environment bootstrap so the quality gate is real, not red-on-arrival:
   ```bash
   bash scripts/setup-env.sh
   ```
   This installs Node deps and the Python deps (`python-docx`, `openpyxl`, …)
   that the DOCX-export smoke step needs. Without them `npm run check` fails at
   the formal-export step with a misleading `500` — that is NOT a code bug.
2. Read `GOAL.md`. It is the north star: the single active objective, the
   definition of done, and the explicit non-goals. Do not start work that does
   not serve the current objective in `GOAL.md`.
3. Read `docs/tasks.md` for the concrete current task list.
4. Read the relevant spec, using the Source-of-Truth hierarchy below.

## 1. Project Mission

Build a Data Center / machine-room **pre-sales AI agent** for construction
integration teams. It turns messy WeChat-style project notes, internal
knowledge, historical proposals, and equipment docs into a structured, editable,
evidence-backed, quote-ready requirement sheet, and eventually a polished Word
export.

The agent should behave like a senior Chinese data center pre-sales director:
practical, commercially aware, fluent in machine-room construction language, and
focused on reducing friction rather than asking long forms.

Current stage: local-first MVP that is past toy stage (real backend, SQLite,
optional real LLM, real DOCX export). Long-term direction: SaaS. **We are NOT
building SaaS infrastructure right now** — see `GOAL.md`.

## 3. Repository Map

- `src/` — React/Vite frontend. The shipped UX is **Presales Workstation V2**: a
  three-column project cockpit (left project pool / center cockpit / right
  presales operations rail). Chat is subordinate to project state.
- `server/` — Node/TypeScript backend: sessions, projects, SQLite persistence,
  OpenAI-compatible LLM client, knowledge retrieval, DOCX export.
- `scripts/` — knowledge ingestion + DOCX render utilities + `setup-env.sh`.
- `knowledge/` — seed local knowledge files (ingested by `kb:build`).
- `src/generatedKnowledge.ts`, `server/generatedKnowledge.ts`,
  `server/generatedKnowledge.json` — GENERATED by `npm run kb:build`. Never edit
  by hand. (They are gitignored.)
- `docs/` — living project memory (architecture, decisions, tasks, roadmap,
  tech-stack, deployment) + `docs/superpowers/` historical plans/specs.
- Root big specs (`api_spec.md`, `rules.md`, `knowledge_base.md`, `templates.md`)
  — mostly FUTURE design. See §4.

## 4. Doc Status Legend — DO NOT mistake design for reality

Every large spec carries a STATUS banner at its top. Honor it:

- **IMPLEMENTED** — reflected in code. Safe to rely on.
- **PARTIAL** — some of it is built; verify against code before relying on it.
- **FUTURE / ASPIRATIONAL** — a design target, NOT current behavior. Do not
  assume these features exist. `rules.md`, `knowledge_base.md`, `templates.md`,
  and most of `api_spec.md` are FUTURE-heavy. The real risk engine is ~2 rules;
  the real RAG is local hashed vectors; the real export is a first-pass renderer.

`docs/specs-future/README.md` is the registry that records, per spec, how much is
actually built. When in doubt, grep the code — never assume a spec is wired.

## 5. Development Flow (per task)

1. Confirm the task serves the current `GOAL.md` objective. If not, stop and ask.
2. Read the required context (§0).
3. For non-trivial work, write a short plan first.
4. Implement the **smallest coherent change**. No drive-by refactors.
5. Run the relevant verification command (§7). Get to GREEN.
6. Update `docs/tasks.md` (status/priority) and `docs/architecture.md` /
   `docs/decisions.md` when design changes.
7. Summarize what changed, how it was verified, and what remains.

## 6. Guardrails

Product:

- Prefer chat + chips over large forms.
- Dashboard edits are the highest-precedence source of truth. Never overwrite a
  `dashboard_edit` value without explicit user confirmation.
- Field precedence: `dashboard_edit > user_message > upload > button_chip >
  agent_inference > default`. LLM candidates use `agent_inference` only.
- Clearly distinguish confirmed values from inferred ones.
- Keep local knowledge citations visible when generated content depends on
  retrieved context.
- The 99 RMB flow is **payment-WILLINGNESS validation only** — never integrate a
  real payment provider. In V2 the main cockpit hides explicit price copy; the
  backend gate still records willingness.

Technical:

- TypeScript types are the contracts between UI, mock API, and backend.
- Keep generated knowledge separate from handwritten code.
- Mock mode (`src/mockApi.ts`) and backend mode (`server/`) are parallel
  implementations — when you change session/field/export behavior in one, keep
  the other aligned or explicitly note the divergence.
- Run `npm run build` before handing off frontend/ingestion changes.
- Run `npm run kb:build` after changing `knowledge/`,
  `scripts/build-knowledge-index.mjs`, or the extraction scripts.
- Preserve the local-first MVP path while keeping module boundaries SaaS-ready.

Scope control:

- Do not start feature work until the objective, architecture, and task state
  are clear. Planning/alignment beats premature code.
- Keep changes tightly scoped. Avoid broad refactors unless the task requires it
  or the structure blocks safe progress.
- Do not "fix" a failing gate before confirming it is a real code bug and not a
  missing-dependency / environment issue (run `scripts/setup-env.sh` first).

## 7. Verification Commands

```bash
bash scripts/setup-env.sh   # make the gate real first
npm run check               # lint + format:check + build + kb:verify + tests
npm run api:smoke           # backend skeleton end-to-end (incl. DOCX export)
npm run kb:build && npm run kb:verify   # after knowledge/ingestion changes
```

## 8. Documentation Guardrails

Update docs when: a module boundary changes; a dependency/runtime is added; a
feature enters or leaves scope; a decision is made or reversed; a task is
completed, blocked, or reprioritized. Prefer concise living docs over exhaustive
prose. Docs should help the next agent resume accurately.
