# Tech Stack

## Current Stack

### Frontend

- React 19
- TypeScript
- Vite
- Lucide React icons
- Plain CSS
- ESLint for TypeScript/React code checks
- Prettier for code formatting

Why:

- Fast local iteration.
- Strong enough typing for session contracts.
- Minimal dependencies.
- Easy to run as a local prototype.
- A small lint/format baseline reduces drift before larger backend/export work.

### Local Knowledge Ingestion

- Node.js script for indexing orchestration.
- Python helper for DOCX/PDF text extraction.
- Python helper for XLSX/CSV/TSV quotation and BOQ extraction.
- `python-docx` when available.
- `pdfplumber`, `pypdf`, or `pdftotext` fallback for PDFs.
- `openpyxl` for XLSX files.
- Python standard `csv` module for CSV/TSV files.

Why:

- Python has mature document parsing libraries.
- Node script integrates cleanly with the Vite project.
- Generated TypeScript index keeps the frontend simple during MVP.

### Current Retrieval

- Backend API mode uses hybrid keyword/vector scoring over the runtime index in `server/generatedKnowledge.json`.
- Frontend mock mode still uses browser-side hybrid scoring over `src/generatedKnowledge.ts`.
- Local hashed embedding vectors generated by `scripts/build-knowledge-index.mjs`.

Why:

- Easy to inspect.
- Mock mode still needs no server.
- Backend mode keeps retrieval behind the API boundary for SaaS migration.
- Runtime JSON lets admin uploads hot-reload backend retrieval without rebuilding the frontend.
- Keeps internal content local while improving recall beyond exact keyword matches.
- Good enough to validate product flow and document source display before choosing a real embedding provider.

## Planned Stack

### Backend

Selected for the first skeleton:

- Node.js
- TypeScript
- Built-in `http` server
- SQLite runtime persistence via Node `node:sqlite`
- Backend-side `ExportPayloadV1` schema and builder for Word rendering
- Admin knowledge upload endpoint for seed trials

Why:

- Keeps API contracts close to the React/TypeScript frontend.
- Avoids adding a backend framework before endpoint boundaries stabilize.
- Provides a lightweight path to SaaS-oriented session APIs.
- Freezes document-generation inputs and keeps the first `.docx` renderer small.
- Adds restart-safe local persistence without committing to a larger SaaS database stack yet.

Python remains useful for document ingestion and may still be used for future RAG/export services.

### RAG

Current MVP:

- Local hashed vectors: `local-hash-v1`, 96 dimensions.
- Runtime JSON index for backend retrieval reload.
- No external embedding API.
- No persistent vector database.

### LLM Agent

Current backend mode:

- OpenAI-compatible Chat Completions over Node built-in `fetch`.
- Runtime configuration through `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`, and `OPENAI_TIMEOUT_MS`.
- Default base URL: `https://api.openai.com/v1`.
- xingwan/New API relay example: `OPENAI_BASE_URL=https://xingwan.store/v1`.
- No SDK dependency, streaming, tools/function calling, or Responses API in the first version.

Why:

- Keeps the first real AI step provider-compatible and small.
- Lets seed deployment use relay platforms without baking provider code into the app.
- Preserves current rule/RAG behavior when no key is configured or the provider is unavailable.

### Seed Deployment

Selected for the seed trial:

- Private GHCR images for API and web.
- Docker Compose for single-server orchestration.
- Caddy for static frontend hosting, HTTPS, reverse proxy, and Basic Auth.
- Separate Caddy Basic Auth credentials for `/api/admin/`.
- Docker named volumes for uploaded knowledge, generated exports, and Caddy state.

Why:

- The seed server does not need the source repo.
- Image tags make update and rollback explicit.
- Caddy keeps HTTPS and access control in the Compose deployment boundary.
- Volumes preserve operational data across image upgrades.
- The team can validate product value before investing in SaaS infrastructure.

Legacy fallback:

- Nginx static hosting and reverse proxy.
- `systemd` for backend process supervision.

Use the fallback only when Docker is unavailable.

Candidate vector stores:

- Chroma for simplest local development.
- Qdrant for robust local/server deployment.
- PostgreSQL + pgvector if the project already needs relational storage.

Candidate embedding models:

- Local Chinese-capable embedding model for privacy-first deployments.
- Managed embedding API if privacy and network policy allow it.

Decision pending.

### Document Export

Current first-pass renderer:

- Python `python-docx` for direct Word generation from `ExportPayloadV1`.
- Node/TypeScript orchestration in `server/exportDocument.ts`.
- Generated files stored under `output/doc/` and served by `/api/assets/{asset_id}/download`.
- Asset metadata persisted in SQLite so the download route can recover after API restart.

Still candidate/future approaches:

- Markdown-to-docx pipeline with strict template QA.
- Dedicated document rendering service later if fidelity becomes complex.

LibreOffice/`soffice` is needed for automated DOCX-to-PNG visual QA. It is not currently available in this local environment.

## Dependency Policy

Add dependencies only when they remove real complexity or support a near-term milestone. Avoid adding full frameworks for features still in discovery.

When a new dependency is introduced:

- Document it here.
- Note the reason in `docs/decisions.md` if it affects architecture.
- Add a verification command or usage note.

## Known Technical Gaps

- No browser/UI automation test runner is configured.
- Backend runtime is still a controlled pilot skeleton and is available through optional frontend backend mode.
- Real LLM integration is first-pass, uses low-precedence field candidates only, and still needs real pilot prompt tuning/provider comparison.
- No real embedding model or vector database exists.
- No legacy `.xls` ingestion exists.
- No automated visual DOCX render QA exists until LibreOffice/`soffice` is installed.
- Free preview PDF remains simulated.
- No tenant, authentication, or permission model exists.
